# P08A 真实项目适配设计（已批准）

日期2026-11-09。依据已批准P08规格第P08A-4/5条：资源库存或模型输入/补丁方式变化须先写明兼容、哈希、范围及预算影响并确认。用户回复“继续”批准本设计；开始P08A后续实施，P08B仍未授权启动。

## 实测原因

固定版本已下载并校验HEAD、干净工作区和实际文件摘要。原修复器把全部批准源码与可见测试文本发给模型，输入上限16000字符、输出上限2048词元；四项目仅包源码即超限，MarkupSafe加测试也超限：

|项目|包源码字符|包源码+上游Python测试字符下界|
|---|---:|---:|
|Click|360096|547699|
|Jinja|503338|786098|
|ItsDangerous|43545|59924|
|MarkupSafe|13860|25211|
|dateutil|279194|718472|

这些是当前Windows固定工作副本的静态字符数，尚未计入系统提示、日志和需求，不是词元数；详见evidence/p08a-preflight.json。实际还涉及模板/数据、fixture和依赖。五项目的三个自编基础探针均已在Docker通过，但不能据此声称完整上游回归通过。

## 推荐方案及替代

推荐：**完整项目仍在容器执行，模型只看可追溯的函数上下文，由可信宿主把函数提案回填为完整文件**；资源作为明确只读库存单独登记。保持现有模型16000字符/2048输出上限、标准FileProposal、哈希与事务校验。

替代一是提高输入/输出到足以容纳整包和上游测试；这会显著改变成本、组间公平与服务上下文要求，仍不解决非Python资源库存。替代二是换成只有小文件的项目或抽出函数单独执行；前者需重新验证五项目配额，后者不能证明原包环境中的修复。因此本稿建议优先函数范围适配，不改变五项目候选和正式样本目标。

## 1. 只读执行资源库存

计划为stage_snapshot/run_tests/run_repair_session增加可选关键字参数`support_files=()`，默认空保持现有行为。它是从受审任务清单取得的**文件相对路径元组**，文件位于同一个独占工作副本；不接受模型提供的路径或宿主任意目录。

- Repository.source_files/test_files仍表示批准的Python源码/测试，字段和CONTRACT_VERSION=1.0不变。Python fixture（含审核conftest）在test_files显式列入；禁止将.py藏入support_files。
- support_files只允许审过的模板/静态数据等非代码文件，精确路径和字节SHA-256写入实验清单；拒绝绝对路径、链接/reparse、受保护目录、重复/大小写冲突、越界及可执行库/程序（.exe/.dll/.so/.pyd/.sh等）。不能仅凭扩展名自动批准整个目录。
- 延续现有每文件1MB、总库存10MB、最多2000文件上限，需放宽另提变更。全部源码+测试+support统一按原路径/字节哈希算法排序计算执行摘要，manifest保存完整清单；空support时旧摘要不变。
- 支持文件只读复制进容器；补丁仍只能替换批准源码，不能改测试、资源、配置、依赖或正确参考。运行环境继续禁网、非root、限资源，无宿主回退。
- 可信参考、缺陷、修复及独立验证使用同一套支持文件；缺失/冲突明确终止，不能悄悄缩小执行集。二进制数据不进入模型文本。

不会因此自动导入任何上游pytest配置/安装插件：已有固定pytest.ini保持受控；必要fixture/插件依赖另审核并固定。MarkupSafe先固定Python后端，原项目代码仍完整，不执行C加速补丁。

## 2. 有界模型上下文

新增实验专用上下文构建器，读取已冻结副本和AST，输出目标函数/方法、必要导入及关联符号/可见测试片段、独立需求和当前失败摘要，附每片段原始路径、行范围、原文件哈希与遗漏清单。允许整文件执行但只展示部分文本，不将片段冒称完整文件。

- 生成器仍返回现有完整新增测试FileProposal；只改变实验构建的GenerateInput.source_texts和显式只读相关测试内容，不改变P06/P07的build_context默认行为。
- 修复上下文在可信宿主保留全部当前源码、可见测试、support哈希，用于重算并核对failed_run.snapshot_digest；模型只获得预算内片段。独立保留内容、正确源码和注入diff不进提示。
- 全请求仍由ModelClient严格检查16000字符，输出2048词元。不截断当前目标函数后假装完整，目标和必要信息放不下就记录context_budget失败，纳入筛选/失败统计。
- 测试执行范围不由模型上下文决定。看不到的已批准模块/原有测试仍参与容器回归。
- 精简日志保留当前失败身份与可定位证据、行映射和截断说明；不把无限日志填满请求，也不让模型改执行命令。

### 上下文选择固定规则（p08-context-v1）

1. 只使用冻结任务指定的一个目标限定名，不由模型输出或本次覆盖率选择目标。按AST建立模块/类/函数索引；同一限定名多次定义、动态覆盖、重载或嵌套闭包目标排除并记录，不猜最后一次生效定义。
2. 必选完整独立需求、完整去装饰器目标定义、所在类名/基类/原签名和位置映射、当前文件/全快照身份。独立需求JSON片段上限2000字符，目标片段6000，类/签名映射1500；超任一项就标context_budget不发请求，不截断必选项。原装饰器文本以只读元数据附在该映射中，不让模型重写。
3. 修复时增加当前第一个失败测试的身份与断言/栈摘要，排序按(classname,name)，最多2000字符，固定保留前1400及后400并加截断标记（总计不超过2000字符）；宿主仍用完整失败签名判断可复现，不用截断日志替代真实证据。
4. 可选项依次为：目标原模块导入语句（按原行号，上限1000）；目标AST直接Name引用的同模块符号签名/首段文档（不递归，上限1500，按路径/原行号）；可见测试函数（上限2500，第一优先显式调用目标函数或同名方法，其次导入目标模块，最后其他测试；每组按路径/行号）。只装入完整可选片段，记录每个未装入片段的路径/行号/原因。调用的语法判定是确定的近似，不宣称解决动态依赖。
5. 第二轮生成在相同算法中把第一轮生成测试优先于原有测试，同一组内仍按上述排序；所有测试仍完整保留在执行集。B2与A0仅一个独立coverage_hint字段不同，其JSON最多1500字符，按path、missing_lines、missing_branches排序列出并明确裁剪。A0不提供该字段，也不额外利用空出的空间装更多代码。B1第一轮与B2/A0第一轮规则相同；修复阶段的上下文算法同一版本，不增加独立保留结果。
6. 预算针对实际序列化messages字符数（含系统提示、JSON转义和身份元数据）计算。先装必选项，再按固定顺序尝试可选片段；为B2/A0两组统一预留1500字符反馈空间及200字符截断说明，超完整16000上限立即拒绝。上下文选择版本、入选/遗漏和实际字符数逐轮保存，正式运行中不根据成功率调参数。

指定函数范围会降低定位难度：行定位只统计范围内诊断，不称全仓自动定位，函数/文件已由任务给定的Top-1/3不得作独立定位成功率。该限制写入实验结果。

## 3. 函数修复提案与可信回填

新增实验专用ScopedRepairer，实现既有repair(RepairInput)→RepairOutput；P05/P06/P07仍使用原Repairer。新增实验wire版本p08-scoped-repair-v1：task_id、base_revision、based_on_run_id、diagnosis、replacements（每项path、qualified_name、content）。它不是新FileProposal协议，模型不提供可信哈希。

第一版每次只接受一个已选定函数/方法的**去除装饰器、从def/async def开始的完整定义**；原装饰器由宿主只读保留，不要求模型同时返回它们。支持唯一模块级函数和唯一类限定名下的普通/async方法；原有staticmethod/classmethod等装饰器保留不变。拒绝嵌套闭包、条件/重复/overload同名定义、无法唯一定位的限定名；不支持跨文件重构、修改签名/装饰器/模块导入。合资格函数在正式冻结前统一筛选，不能依据模型成功与否排除。

可信回填步骤：

1. 使用本次可信RepairInput的完整当前文件、最新失败摘要及任务允许的函数身份，验证全文件SHA和原函数字节范围；不复用旧行号。
2. 模型定义去除公共缩进后只能包含一个同名同类型FunctionDef/AsyncFunctionDef，无额外顶层语句/装饰器，参数及返回注解AST与原定义一致。
3. 宿主按原AST定义范围回填、恢复方法缩进（AST列偏移为UTF-8字节偏移，必须从原字节切片映射，不当作Unicode字符索引），原装饰器和目标范围以外字节（含换行）保持不变；整模块重新ast.parse。范围内可有函数内部导入，不能添加模块级导入。
4. 构造完整文件FileProposal，expected_sha256由可信当前字节计算；继续validate_proposal、apply_proposal、事务/回滚和完整可见/保留执行。模型提交其他函数/文件、过期run、越范围内容均拒绝。

run_repair_session计划增加可选`repairer_factory=None`，为空仍创建原Repairer；实验提供受审的ScopedRepairer工厂。support参数传递到每次复制/执行和只读验证；实验的完整快照校验包含support哈希，不能只对片段做摘要后冒充完整输入。

同一项目/任务所有B1/B2/A0组都使用同一范围适配，避免只给某一组更丰富上下文。覆盖率明确选择被测项目源码，排除Jinja所带MarkupSafe等依赖源码，不把任务函数覆盖率称整项目覆盖率。

## 4. 前置反馈与兼容

按照已批准P08规格实现独立实验编排：B1一轮，B2/A0两轮累计测试后再修复。两组除覆盖率提示外保持同一上下文选择/预算/回填规则；子任务保留父测试与源码摘要，合法状态不可复活。P06/P07现有修复后反馈不变。

新实验清单schema独立版本化，区分mutable源码、不可改测试/support、目标函数和被测项目coverage范围；不得把所有依赖都当可修源码。资源依赖和模型片段有各自库存与审计记录，不借此放宽默认冻结任务入口。

## 5. 必须先通过的验证

- 空support时P03/P06/P07的输入摘要、默认API和真实重放不变；新增支持文件缺失/篡改、symlink/junction、重名/代码伪装全部拒绝。
- ScopedRepairer拒绝错文件/错函数/过期哈希、改签名/装饰器/模块注入；验证方法缩进、Unicode、CRLF、函数尾注释和范围外字节不变。仅语法正确不算语义正确。
- 原包__file__来自工作副本；固定依赖和MarkupSafe后端，防止调用镜像正确包。记录上游完整套件/审核子集和所有排除。
- 有界上下文包含原始位置并记录遗漏，超限终止且不发模型请求；失败签名、全库存摘要与最新run绑定。
- 两类受控预跑、三边界回归及一项真实项目端到端/前置反馈对照；独立语义复核。不因此开始P08B。

## 批准后工作顺序

先资源库存及兼容回归，再有界上下文/函数回填，再真实项目受审回归和前置反馈。实际文件/签名与红绿测试补入P08实施计划，各检查结果同步总表。批准本适配只继续P08A，不批准正式30任务批量，也不表示五项目完整测试已通过。


独立可实施性检查：review_p08a_checkpoint提出并已补齐上下文确定性规则、去装饰器定义/限定名资格和UTF-8字节列偏移要求，增量复核无新增重要问题；此为批准前的历史检查；用户随后“继续”批准并实施。当前技术验证完成、待用户验收P08A，P08B未开始。
