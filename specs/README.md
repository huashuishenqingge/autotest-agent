## 工作方式

1. 负责人为阶段写Spec：目标、范围、输入输出、规则、验收场景、任务依赖与分工。
2. 用户确认Spec后才能据此新增或改变实现；文档草案不自动授权开发下一阶段。
3. 实施人领取进度表中的任务编号，记录分支和姓名；测试覆盖Spec验收编号。
4. 完成后关联Spec条款、变更文件、实际命令、结果和证据；另一成员交叉复核。
5. 用户验收后结束该阶段；同时更新Spec验收表及唯一进度总表。

需求来源优先级：用户最新明确指令 > 已确认规格 > 开题报告 > 代码。未确认的草案不能覆盖已批准需求。现有代码只是被验证对象，不是需求正确性的依据。出现冲突记录差异，由用户确认会改变验收范围的调整。

## 文档与状态边界

- 需求规格：系统级稳定要求及对应阶段。
- 接口契约：现有接口边界与应用层规则，不能在文档中悄悄更改代码协议。
- P03-隔离执行：当前阶段的可执行验收场景和未完成项。
- 项目计划与进度：任务负责人、实施状态、阻碍和交接的唯一总表。Spec只记录条款与验收证据，不复制另一份任务进度。
- 阶段验证与交接：历史运行证据。历史“成功”不代表当前环境复验成功。

变更规格时记录：变更日期、条款ID、原因、影响模块及测试、是否更改验收范围、批准记录。接口字段/枚举变更还须评估CONTRACT_VERSION，协调两人调用方。
